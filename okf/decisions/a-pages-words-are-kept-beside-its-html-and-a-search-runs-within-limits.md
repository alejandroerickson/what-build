# A page's words are kept beside its HTML, and a search runs within limits

## Context

Plain search stripped the markup of every current page on every search, and the expression that did
it could run for minutes on a page of many script or style blocks. Each stuck search held one of the
server's connections, so a few of them left ordinary requests waiting with no end, while the health
check, which reads no database, went on answering. The expression also lost the words between two
blocks of the same kind. Three ways to keep the words were live: a worker job, which can run late,
fail and need cleaning up; extracting them in TypeScript when a page is saved, which needs a job to
fill in existing rows; and generated columns.

## Decision

- `mockup_pages` and `story_versions` carry `search_text` and `tsv`, generated by Postgres from
  `html` through `html_search_text` and `words_search_vector` (migration `0040`). They are written by
  the statement that writes the HTML, so there is no separate step to run late, fail or collide with
  another save, and no cleanup job. A version is immutable, and search reaches the current one through
  the same pointer that makes it current.
- The words are capped at 200,000 characters a page. HTML past the words (styles, scripts, paths,
  data: URIs) costs nothing against the cap.
- No page's words can make a save or the migration fail with an error. Postgres refuses a vector past
  1 MB of lexemes, and what a character costs depends on how its parser reads it. So
  `words_search_vector` tries, catches what Postgres raises on text, and tries again on three quarters
  of the text, rather than cutting the text to a bound worked out from the parser, which would cost
  every page words to guard against pages nobody writes and would be as true as that working out. That
  is worth a millisecond on each save. How long a rewrite of every page takes is not bounded by this:
  it grows with what a deployment holds and pages vary in cost, so a deployment sizes what it holds
  first, and a job killed for time leaves nothing changed and can be run with longer.
- The vector's parser reads no `<`, and no run longer than 255 characters, since a page's words are not
  markup. That keeps the time of a save, and of a migration that rewrites every page, in proportion to
  the words. The cut falls where a word already ends, whenever one does within those 255 characters,
  since a cut anywhere else splits a word into two that nobody searches for, and a list with no spaces
  or a language written without them is ordinary text. What ends a word is written out in the function
  rather than left to a regular expression's character classes, which follow the database's locale.
  Fixing this later would mean rewriting both tables again.
- What a search vectorizes when it runs goes through the same function. A brief has no stored vector,
  and a slow one would hold one of the few slots a server has for every organization until its time
  limit, so the protection a stored vector gets is worth about a microsecond on each row a search
  reads. A mockup's own text is read once, not once for each of its pages.
- An entity that stands for a letter is that letter in the words, named or numeric, so `caf&eacute;`
  is found as `café`. Any other entity is a word break, so `&lt;`, `&gt;` and `&amp;` never become
  characters a reader of the words could take for markup. The function cuts the text with plain string
  functions rather than a regular expression, whose cost per match adds up on every save, and holds
  its tables itself, since a table or a helper function of ours
  would not resolve when a backup restores with an empty `search_path`.
- The migration takes both tables' locks before it does anything, and never waits long holding one.
  The app reads the two tables in both orders within a transaction, so no order of locks suits every
  read, and a migration waiting for the second with the first in hand can deadlock with one. Each try
  gives each lock 200 ms and lets go, so a read waits a fraction of a second and nothing is ever a
  deadlock's victim, and each try takes them in the other order from the last, so traffic running
  mostly one way meets the order that suits it at once. Two minutes of that end the migration with an
  error, having changed nothing. Waiting longer would not help steady traffic both ways, which can
  leave no moment for either order, and would come out of the time the rewrite has: such a deployment
  runs it at a quieter time, or holds traffic off for the moment it needs.
- No GIN index on `tsv`: search reads one product's current pages, found through its mockups and
  Story pages, where one made no measurable difference and would have held every old version too.
- `search` is `bounded`: three at a time on a server, twelve more waiting two seconds at most and
  holding no connection, five seconds for the whole search, and stopped at once when its caller goes.
- Every request waits at most 15 seconds for a connection, then is answered `503 database_busy`.
  Connections held with requests waiting, across two looks ten seconds apart, are logged as an ERROR.

## Consequences

- Search's cost no longer grows with how much markup a product holds. A save costs a few more
  milliseconds, and a change to the extraction is a migration that rewrites both tables.
- A search can answer `503` where it once hung; that says nothing about whether the words exist.
- The limits are per server, so each replica has its own.

## Constrains

- Plain search reads `search_text` and `tsv`, never `html` (`packages/core/src/ops/plain-search.ts`).
- Neither column is in an answer or an export (`packages/core/src/ops/export.ts` drops them).
- A new kind of HTML to search gets the same generated columns, not stripping at request time.
- A search vector over a page's words, or computed when a search runs, goes through
  `words_search_vector`, never `to_tsvector` directly.
- A migration that rewrites both tables takes their locks the way `0040` does.
- An operation that may run long for reasons its caller controls is `bounded`
  (`packages/core/src/bounded-search.ts`), which sets its limit for its own transaction alone.
